# Deep scan module with API vulnerability scanning and advanced payload generation

This change adds a DeepScanModule that orchestrates multi-technique scanning with automatic API vulnerability detection. When a target is fingerprinted as an API endpoint (by URL pattern or content-type), the module runs six OWASP API Top 10 tests: BOLA/IDOR, broken authentication, injection (SQL/NoSQL), mass assignment, excessive data exposure, and rate-limit bypass. Supporting this, the crawler gains six new parameter extraction methods (JSON body parsing, multipart discovery, WebSocket endpoint detection, API version enumeration, response-header mining, and deep JS analysis), and the evasion module gets a `generate_context_payloads` method that selects and mutates payloads based on WAF presence, reflection context, and technology stack. Ten new payload lists cover polymorphic SQLi, mXSS, blind XSS callbacks, context-aware XSS by reflection type, SSRF bypass tricks, command injection polyglots, PHP filter chains, and SSTI sandbox escapes.

**Watch for:** BOLA test sends the modified ID in the `data` dict but never rewrites the URL path, so path-based IDs (`/users/5`) won't actually vary between probes (confirmed). The broken-auth test has no baseline comparison — it flags any 200 response with >20 bytes as broken auth without checking whether the endpoint is public by design (confirmed). The rate-limit test fires only 5 requests — practically every endpoint will pass 5 requests without triggering a 429, producing high false-positive rates (confirmed).

## High-level view

The DeepScanModule's `test()` method is a sequential pipeline: fingerprint → API vuln tests → recursive param discovery → chained attacks → WAF bypass → second-order injection. The fingerprinting step determines everything downstream — the `is_api_endpoint` flag gates the entire API scanning branch, and `waf_detected` controls the WAF bypass branch. The fingerprint itself is accurate for the common case (JSON content-type or `/api/`, `/v1/` URL segments) but doesn't inspect response structure.

The API vulnerability tests implement the OWASP API Security Top 10 categories most relevant to automated scanning. Each test is self-contained, issues its own requests, and reports findings via `_add_finding`. The BOLA and broken-auth tests have structural issues: BOLA doesn't substitute the ID into the URL for path-parameter APIs, and broken-auth has no concept of "this endpoint is intentionally unauthenticated." Mass assignment and injection detection work through response-signature matching and are more reliable.

The crawler extensions add breadth by mining parameters from JavaScript (fetch bodies, FormData, destructuring, GraphQL variables, route definitions) and from response metadata (Link headers, JSON keys, pagination patterns). The response-params extractor is aggressive — every JSON key in a response body and every `X-*` header becomes a testable parameter, which could generate significant scan noise on verbose APIs.

The payload configuration is a static catalogue: context-aware XSS payloads are keyed by reflection type (`html_attr`, `js_string`, `url_context`, `css_context`), and `generate_context_payloads` on PayloadMutator selects the right list based on `vuln_type` + `context_info`. When WAF is detected, it doubles the payload count by appending double-encoded and unicode-normalized variants.

Test coverage is broad (95 tests, all passing) but focuses on happy-path detection. The tests don't exercise the false-positive scenarios that the detection logic will encounter in production.

<summary>Issues (7)</summary>

1. **BOLA path-parameter blind spot** — When the ID is in the URL path (e.g. `/api/users/5`), `_test_bola_idor` passes `data={param: test_id}` which appends it as a query param for GET. The path segment never changes, so the test never actually accesses a different resource. Parse the URL and substitute the path segment when the param appears in the path.
2. **Broken-auth false positives on public endpoints** — `_test_broken_auth` flags any 200 response without the word "unauthorized" as broken auth. Public endpoints (health checks, docs, unauthenticated listings) will trigger this. Add a baseline comparison: if the endpoint returns the same data with legitimate auth, it's public by design.
3. **Rate-limit 5-request threshold too low** — Most APIs allow burst windows well above 5 requests. This test will flag nearly every endpoint as lacking rate limiting. Either raise the threshold significantly or compare against the documented rate window.
4. **Response-param extraction noise** — `_extract_response_params` registers every JSON key from the response body as a GET parameter. On a verbose API returning 50+ fields, this generates hundreds of parameters to test, most of which are response-only fields that the server won't accept as input.
5. **Payload explosion under WAF detection** — When WAF is detected, `generate_context_payloads` appends the full polymorphic list *again* (duplicating it), then double-encodes and unicode-normalizes every payload. For SQLi with WAF, this produces ~96 payloads per parameter. Combined with `_adaptive_waf_bypass` limiting to 5, the extra generation is wasted.
6. **Second-order timing threshold fragile** — `_test_second_order_deep` flags any follow-up response taking >4s as potential second-order blind SQLi. Network latency or server load will produce false positives at LOW confidence. The threshold should be calibrated against the baseline response time from fingerprinting.
7. **Duplicate multipart parameter entries for file inputs** — `_extract_multipart_params` appends the file input name twice (once in the generic loop, once in the special file-input branch). This doubles scan work for file upload fields without benefit.

## BOLA/IDOR detection and the path-parameter gap

The `_test_bola_idor` method correctly identifies numeric and UUID parameter values as ID candidates, then probes adjacent IDs to detect unauthorized access. The logic is sound for query-parameter APIs: the requester's `_dispatch_request` passes `data` as `params=` for GET, so `{param: test_id}` becomes `?id=6` on the URL. But REST APIs that embed the ID in the path (`/api/users/5`) pass the param name as `"id"` with value `"5"` — and the probe just appends `?id=6` while the path still says `/users/5`. The server resolves the path segment, ignores the query param, and returns the same resource for every probe. The test then correctly sees "same content" and reports nothing — a silent false negative on the most common API pattern.

```python
# Current: always sends data={param: test_id} — only works for query params
resp = self.requester.request(
    url, method,
    data={param: test_id} if method == "POST" else None
)
# For GET with path params, url itself must be modified
```

The fix requires detecting whether the param value appears in the URL path and, if so, performing string substitution on the URL rather than passing it as data.

## Broken-auth test without baseline context

`_test_broken_auth` sends requests with empty/null auth headers and flags a finding whenever the response is HTTP 200 with >20 bytes and doesn't contain error keywords. There's no comparison against an authenticated baseline — the method doesn't know whether the endpoint requires auth in the first place. A public status page, an OpenAPI spec endpoint, or a documentation route will all trigger this finding at MEDIUM confidence.

The `_test_api_vulnerabilities` dispatcher calls `_test_broken_auth` on every API endpoint detected by fingerprinting. Since fingerprinting just checks for `/api/` in the URL or JSON content-type, many legitimately public endpoints will be flagged.

## Rate-limit detection at 5 requests

The `_test_rate_limit` method sends 5 sequential requests and reports "missing rate limiting" if all return 200. Five requests is well within the burst tolerance of any real rate limiter — most allow 60-100+ requests per minute by default. This makes the test effectively a "does the endpoint respond" check rather than a meaningful rate-limit assessment. The LOW severity and MEDIUM confidence are appropriate, but the finding will appear on every scannable endpoint, drowning real issues.

## Response-params extraction and scan amplification

`_extract_response_params` iterates all JSON keys matched by `r'"(\w{2,30})"\s*:'` in the response body and registers each as a testable GET parameter. For a typical JSON API response with nested objects, this can produce 30-100 parameters per page crawled. Many of these (e.g. `"created_at"`, `"avatar_url"`, `"total_count"`) are output-only fields that the server doesn't accept as query params. The scan engine will then test each with multiple modules, multiplying total requests dramatically.

The `_JS_NOISE` filter is applied in the JS-mining methods but not in `_extract_response_params`. Adding a similar noise filter for common output-only field names would reduce scan amplification.

## Payload generation doubling under WAF conditions

In `generate_context_payloads`, when `vuln_type == "sqli"` and `waf_detected == True`:

```python
payloads = list(Payloads.SQLI_POLYMORPHIC)            # 16 items
payloads.extend(Payloads.SQLI_CONDITIONAL_ERRORS)     # +12 = 28
if waf_detected:
    payloads.extend(Payloads.SQLI_POLYMORPHIC)        # +16 = 44 (duplicates!)
# Then:
if waf_detected:
    mutated = []
    for p in payloads:  # 44 items → 88 mutations
        mutated.append(self._mutate_double_encode(p))
        mutated.append(self._mutate_unicode_normalize(p))
    payloads.extend(mutated)  # 44 + 88 = 132 total
```

The `SQLI_POLYMORPHIC` list is appended a second time, creating 16 exact duplicates. The mutation loop then doubles and unicode-normalizes all 44 (including the duplicates), producing 132 payloads. `_adaptive_waf_bypass` only uses `base_payloads[:5]`, so 127 of these are generated and immediately discarded.

## Chained-attack selection and LFI confidence

The LFI filter-chain test in `_chain_lfi_filter` reports CRITICAL severity at MEDIUM confidence when `len(resp.text) > 1000`. A response over 1000 bytes is not unusual for normal pages — this condition alone doesn't indicate file inclusion. The `root:` check and `<?php` check are strong indicators, but the length-only branch is a false-positive risk that shouldn't carry CRITICAL severity.

## Test coverage gaps

The 95 tests cover the main detection logic well — fingerprinting, each API vuln type, chained attacks, WAF bypass escalation, and second-order injection. What's not tested:

- The path-parameter BOLA scenario (GET with ID in URL path) — the tests only exercise numeric IDs where data dict works
- False-positive scenarios: public endpoints hitting broken-auth, normal latency hitting second-order timing, large responses hitting LFI length check
- `generate_context_payloads` with WAF + specific tech stacks (only the list membership and mutation techniques are verified, not the selection logic under various context_info combinations)
- The crawler's `_extract_response_params` with realistic JSON bodies containing nested objects
